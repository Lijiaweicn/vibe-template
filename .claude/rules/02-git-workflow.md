# 02 - 业务级 Git 提交与变更流转规范

## 一、 核心原则

你的 Git 操作必须完全服务于真实业务交付节奏。允许并鼓励你在单个 Commit 中提交多个关联功能的阶段性开发成果，但必须确保代码通过自动化测试，且禁止擅自进行远程推送（Push）。

## 二、 Commit Message 业务规范

每次提交必须严格遵循企业级业务变更格式：`<type>(需求编号): <subject>`

1. **Scope 必须为需求/任务编号**：
   - **绝对红线**：严禁使用文件路径（如 `core/form`）作为 scope。
   - **取值来源**：必须从当前分支名称中提取需求单号（例如分支名是 `feat/REQ-8894-bidding-logic`，则需求编号为 `REQ-8894`）。如果没有提取到，请优先询问人类，或使用本次迭代的全局单号。

2. **允许的 Type 类型**：
   - `feat`: 交付新业务功能（支持多功能合并提交）
   - `fix`: 修复业务缺陷或联调 Bug
   - `refactor`: 业务代码重构（如逻辑从视图解耦到 models 或封装 LogicHub）
   - `test`: 单元测试/参数化测试的编写与调整

3. **Subject 业务化描述**：
   - 必须使用清晰的中文动宾结构。
   - 针对**多功能并行开发**的提交，必须在 Subject 中用「分号」或「及」将核心交付点打平表述。
   - 示例：`feat(REQ-8894): 建立招标价格校验模型及开发大客户显隐控制功能`

## 三、 变更流转行为红线（Claude Code 业务开发约束）

1. **阶段性本地提交（允许打包）**：当你完成一个或多个功能点、且运行测试全绿后，可以将这些变更打包执行 `git add` 和 `git commit`。不需要刻意为了分步而分步。
2. **绝对禁止自动 Push**：你**绝对禁止**擅自执行 `git push`。所有的远程同步和代码合入，必须在本地闭环交付后，由人类审查并手动推送到远端。
