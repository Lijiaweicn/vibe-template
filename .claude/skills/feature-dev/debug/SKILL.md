# Feature Dev 问题诊断

验收发现问题时触发。先分析汇报，由用户决定修复方式。

## 输入

调用时需提供：
- **问题描述**：用户反馈的具体现象（含预期和实际的对比）
- **相关文件**：涉及的 task 文件路径（可选）

## 执行流程

### 1. 记录问题

将问题信息结构化记录：

```
**问题**：<一句话描述>
**触发路径**：<操作步骤，如"点击按钮 → 页面白屏">
```

### 2. 分析（只读）

基于问题描述，分析可能涉及的代码区域：

- 读取相关 task 文件的"已确定"和 TODO，理解功能上下文
- 读取相关代码文件（domain、component、view），但 **只读不改**
- 列出可疑位置，说明怀疑理由和推断的根因
- 给出一个修复方案

**禁止事项**：此阶段不允许修改任何文件。

### 3. 汇报并选择路径

向用户汇报分析结论：

```
**分析**：<推断的根因>
**方案**：<准备怎么修>

请选择：
A. 直接修复 — 我来验证
B. 先插桩 — 收集日志后再修
```

**⛔ 门禁：必须等待用户选择路径。禁止自行决定跳过诊断。**

---

## 路径 A：直接修复

适用于根因明确、用户愿意快速验证的场景。

### A1. 实施修复

1. 按步骤 3 的方案修复（只改必要的代码）
2. 告知用户改了什么，请用户验证

**⛔ 门禁：必须等待用户验证修复效果。禁止自动假设修复成功。**

### A2. 结果

- **修复成功** → 结束
- **修复失败** → 进入**路径 B**，从步骤 B1 开始

---

## 路径 B：插桩诊断

适用于根因不明确、或路径 A 修复失败需要深入排查的场景。

### B1. 设计插桩方案

为可疑位置设计 console.log 插桩：

- **入口函数**：打印入参、调用时机
- **分支判断**：打印条件值、走的哪个分支
- **数据转换**：打印转换前后的值
- **异步操作**：打印 Promise 状态、返回值

插桩要求：
- 使用 `[DEBUG]` 前缀标记，便于后续识别和移除
- 日志内容要有意义，包含变量名和上下文，不要只打印 `"here"`
- 每个插桩点加一行注释说明为什么在这里插桩

### B2. 插桩并收集日志

1. 按方案插入 console.log
2. 告知用户：
   - 在哪些文件的哪些位置插了桩
   - 需要用户执行什么操作来复现问题
   - 请用户复现后将控制台输出贴回来

**⛔ 门禁：必须等待用户提供日志输出。禁止跳过、禁止假设日志内容。**

### B3. 分析日志

收到用户提供的控制台输出后：

1. 搜索 `[DEBUG]` 标记的日志行
2. 对比实际输出与预期，缩小问题范围
3. 向用户汇报分析结论：日志中发现了什么、推断的根因是什么、准备怎么修

如果日志信息不足以定位，回到 B1 补充插桩点，再次收集。

**⛔ 门禁：必须等待用户确认根因分析。用户未确认前，禁止开始修改代码。**

### B4. 实施修复

用户确认根因后：

1. 实施修复（只改必要的代码）
2. **不要移除插桩代码**，保留 `[DEBUG]` 日志供验证
3. 告知用户改了什么，请用户验证，验证时观察控制台日志

**⛔ 门禁：必须等待用户验证修复效果。禁止自动假设修复成功。**

### B5. 清理

用户确认修复生效后：

1. 移除所有 `[DEBUG]` 插桩代码（包括注释）
2. 告知用户清理完成

如果用户反馈修复无效，回到 B3 重新分析。

## 约束

- **分析只读**：步骤 2 不允许修改任何文件
- **路径由用户选**：禁止 AI 自行决定走路径 A 还是 B
- **日志驱动**：路径 B 的分析必须基于实际日志，不能凭空猜测
- **插桩保留到验证通过**：路径 B 修复后保留插桩代码，验证通过后才清理
- **最小改动**：修复时只改必要的代码，不做重构或优化
