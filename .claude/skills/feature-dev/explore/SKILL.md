# Feature Dev 需求探索

通过 AI 辅助访谈梳理需求，再以对抗性质疑暴露隐含假设。

## 前置条件

无。这是 Feature Dev 流程的第一个阶段。

## 流程

### 1. 信息收集

通过提问梳理需求，每次只问一个问题：

- 这个需求要解决什么问题？
- 涉及哪些模块/页面？
- 有没有参考的设计稿或接口文档？
- 有哪些已知的约束或限制？
- 预期的验收标准是什么？

### 2. 假设质疑

信息收集完成后，读取 `config.yaml` 的 `challenge` 插槽：

- **skill 不为 null**：调用指定的外部 skill（如 grill-me）进行假设质疑
- **skill 为 null**：执行内置质疑模式（见下方）

**内置质疑模式**：

像一个极具攻击性的架构师一样，对用户的假设发起挑战。逐条链路追问，逼用户理清边界条件：

- "你说要做 X，但为什么不用 Y？Y 的优势是..."
- "这个需求的前提条件成立吗？如果前提不成立呢？"
- "如果 Z 发生了怎么办？你的方案能覆盖这个场景吗？"
- "这个功能追溯历史数据吗？存量数据怎么处理？"
- "你确定 scope 是这些？有没有你没想到但用户一定会问的？"

**目的**：不是刁难，是在进入规划前把隐含假设全部暴露出来。

### 3. 产出 README 骨架

将访谈和质疑的结果写入 `docs/feature/README.md`，作为后续阶段的输入：

1. 从当前分支名提取需求标识（去掉 `feature/`、`fix/` 等前缀）
2. 创建 `docs/feature/` 目录和 README.md：

```markdown
# <需求标识或功能名称>

> 需求标识: `<从分支名提取的标识>`

## 核心功能
<!-- 概述性描述，来自访谈结果 -->

## 验收标准
<!-- 粗粒度的功能点描述，标记待深化的项 -->
<!-- 如"登录表单能正常提交"，而非具体场景 -->

## 待确认项
<!-- 质疑中暴露的隐含假设，需要后续确认或开发中验证 -->

## 任务列表
<!-- 由 specify 阶段填充 -->

## 总结
<!-- 由 accept 阶段填写 -->
```

**注意**：任务列表和总结留空，由后续阶段填充。此阶段只写需求描述相关内容。

## 门禁条件

- [ ] 明确了要解决什么问题
- [ ] 明确了涉及哪些模块/页面
- [ ] 明确了验收标准（或标记为待深化）
- [ ] 质疑中暴露的隐含假设已全部记录
- [ ] `docs/feature/README.md` 已创建，包含需求标识、核心功能、验收标准
