# /fix — 问题修复

## When to Use

- 用户报告了一个 bug 或异常行为
- 测试失败
- 行为不符合预期
- 控制台报错

## When NOT to Use

- 想要新功能 → 用 `/dev`
- 不确定是不是 bug → 先用对话探索，确认后再 `/fix`
- 重构代码但行为不变 → 直接改或用 `/dev`

## 流程

### 阶段 1: 问题收集 + 调试准备

- 收集复现步骤、期望行为、实际行为
- 分析代码，在可疑位置添加 console.log 调试日志
- **⏸ 请用户运行复现，提供控制台日志输出**

### 阶段 2: 定位分析

- 根据日志 + 代码分析，定位根因，提出修复方案
- **⏸ 向用户汇报分析结论（根因 + 修复方案），明确询问"这个分析是否符合你看到的现象？"，等待用户确认或纠正**

### 阶段 3: 修复实现

- 按确认后的方案修复
- **⏸ 请用户运行验证，确认问题是否解决**
- 如未解决：根据用户反馈继续调整，回到阶段 2 重新分析

### 阶段 4: 收尾（用户确认问题解决后）

- 清理调试代码（console.log、debugger）
- 执行 `pnpm lint` + `pnpm check`
- 调用 code-reviewer 检查
- 展示变更摘要

## Anti-Rationalizations

| Agent 的借口 | 反驳 |
|-------------|------|
| "加个 if 就行了" | 治标不治本，同类 bug 会再出现。找到根因，修在源头 |
| "先修了再说" | 不理解根因的修复是引入新 bug |
| "这个 edge case 不太可能发生" | 不太可能 ≠ 不可能，线上环境什么都可能发生 |
| "用户说的问题我复现不了就跳过" | 复现不了 ≠ 不存在，先收集更多信息 |
| "改一行代码不需要检查调用方" | 一行改动可能影响所有调用方 |

## Red Flags

- 修复涉及 3 个以上文件 → 可能需要重新分析根因
- 修了 A 又 break B → 根因分析不充分，暂停
- 用户说"还是没解决"超过 2 次 → 换思路重新分析，不要在同一棵树上死磕
- 修复方案是"加个默认值" → 审查是否在掩盖数据流问题
- 修完后没有新增测试 → 无法防止回归

## Verification

完成的证据（缺一不可）：

- [ ] 用户确认问题已解决
- [ ] 调试代码（console.log、debugger）已清理
- [ ] `pnpm lint` + `pnpm check` 通过
- [ ] 修复不会引入新问题（检查调用方）
- [ ] 有测试覆盖该场景（防止回归）
