# VBW 开发执行

基于 VBW 任务文档驱动开发流程，在 feature 分支上直接开发，包含验证清单、review 循环。

## 触发条件

通过 Skill 工具调用（`vbw-dev`）。规划完成后由 vbw-plan 输出引导调用。

## 前置条件

`docs/feature/` 目录下存在已规划的需求文档（由 vbw-plan 生成）。

## 流程

### 1. 定位任务

读取 `docs/feature/README.md`，找到第一个未完成的大任务节点（`- [ ]` 状态的任务链接）。

读取 README 头部的需求标识，用于后续定位。

### 2. 检查依赖

读取任务文件的 frontmatter `depends` 字段：

- **有依赖**：逐一检查前置任务是否已完成（README 中对应项标记为 `- [x]`）
  - 前置任务未完成 → 提示用户先完成前置任务，询问是否切换到前置任务
  - 前置任务已完成 → 继续步骤 3
- **无依赖**：直接进入步骤 3

### 3. 检查待解决

读取任务文件的 **待解决** 部分：

- **有待解决内容**：
  1. 列出所有待解决项
  2. 与用户逐一讨论解决方案
  3. 讨论结果转化为 TODO 步骤，写入 **TODO** 部分
  4. 决策记录写入 **已确定** 部分
  5. 清空对应的待解决项
  6. 全部解决后进入步骤 4
- **无待解决内容**：直接进入步骤 4

### 4. 逐项开发

在当前 feature 分支上直接开发，按 TODO 列表逐项执行：

1. 读取当前任务的 TODO 列表
2. 执行第一个未完成的 `- [ ]` 项
3. 完成后更新为 `- [x]`
4. 继续下一项，直到全部完成

**代码搜索**：查找已有模块、组件、接口时，优先使用 CodeGraph；不可用时回退到 Grep/Glob/Read。

开发过程中：
- **禁止自动 commit**，所有提交由用户手动控制
- 可调整 TODO 列表（添加/删除/修改步骤）
- 遇到新问题可添加到待解决

**暂停条件**：出现以下情况时，暂停当前任务开发，调用 `vbw-plan` 补充任务文档：
- 需要新增大节点 task（改 README 任务列表 + 新建 task 文件）
- 当前 task 拆分不合理，需要拆分或合并
- 需求本身发生变化（背景、核心功能、验收标准）

`vbw-plan` 完成补充后，回到本流程步骤 1 重新定位任务。

**动态拆分子任务**：开发中发现需要拆分子任务时：
1. 新建 `<父slug>-<子slug>.md`（使用完整 task 模板），如父任务 `login-form.md` 的子任务命名为 `login-form-captcha.md`
2. 若新任务是当前任务的前置：当前任务的 `depends` 中加入新 slug
3. 若新任务是当前任务的后续：新任务的 `depends` 中加入当前 slug
4. README 不必改动（除非新任务是大节点，需用户确认后加入 README）

### 5. 验证清单自检

所有 TODO 完成后进行自检（以下清单来自 workflow.md，已在上下文中可用）：

- [ ] 所有 TODO 项已标记 `[x]`
- [ ] 待解决已清空或全部转化为已确定
- [ ] 符合 `workflow.md` Code Review 清单：
  - [ ] models 是纯函数（无 `this`、无响应式 API）
  - [ ] 常量已收拢到 `constants.ts` 并加了 `as const`
  - [ ] 表单场景：`formData` 不含 UI 属性（UI 属性已放 `uiContext`）
  - [ ] 视图模板：无复杂表达式（如 `v-if="a && b"`）
  - [ ] 视图模板：无可选链防御链（如 `data?.xxx`）

**所有项必须通过，否则修复后再继续。**

### 6. 用户人工验收

读取当前任务的**验收清单**，逐项引导用户核验：

1. 展示验收清单（每项为 `- [ ]` 格式）
2. 用户逐项确认或反馈问题
3. 通过的项目标记为 `- [x]`
4. 未通过的项目记录问题，进入修复循环

同时向用户展示：
- 列出本次任务做了什么（关键变更摘要）
- 展示关键代码片段（如有必要）

验收循环：
- 用户发现问题 → 修复 → 重新展示相关验收项
- 所有验收项通过 → 继续步骤 7

**重要**：验收以清单为准，不能跳过或笼统确认（如"看起来没问题"）。

### 7. 更新 README 状态

在 README.md 中标记任务完成：`- [ ] [slug](slug.md)` → `- [x] [slug](slug.md)`

### 8. 循环或收尾

- **还有未完成任务**：回到步骤 1，继续下一个任务
- **所有任务完成**：进入步骤 9

### 9. 需求级一致性检查

写总结前进行最终检查：

- [ ] 每个 task 的已确定内容与实际代码一致
- [ ] README 描述的需求背景和核心功能全部被任务覆盖（对照步骤 1 读取的 README）

**所有项必须通过，否则修复后再继续。**

### 10. 填写总结

在 README.md 的总结区域填写成果提炼：

- 实现了什么功能
- 关键技术决策
- 值得注意的问题或发现

**注意：总结是成果提炼，不是 git log 副本。**

## 异常处理

- **中途中断**：保留当前进度，下次继续时从步骤 1 重新定位
- **需求变更/任务调整**：按步骤 4 的暂停条件，调用 vbw-plan 补充文档后回到步骤 1
- **依赖循环**：执行前检查 depends 是否构成循环依赖，如有则提示用户调整
