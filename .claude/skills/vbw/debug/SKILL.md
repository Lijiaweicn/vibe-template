# VBW 日志优先诊断

验收发现问题时触发。核心原则：**先收集运行时信息，再定位修复。禁止在收集到日志之前修改业务代码。**

## 输入

调用时需提供：
- **问题描述**：用户反馈的具体现象（含预期和实际的对比）
- **相关文件**：涉及的 task 文件路径（可选）

## 执行流程

### 1. 记录问题

将问题信息结构化记录：

```
**问题**：<一句话描述>
**触发路径**：<操作步骤，如"点击按钮 → 页面白屏">
```

### 2. 推断可疑区域（只读）

基于问题描述，分析可能涉及的代码区域：

- 读取相关 task 文件的"已确定"和 TODO，理解功能上下文
- 读取相关代码文件（domain、component、view），但 **只读不改**
- 列出 2-3 个最可疑的代码位置，说明怀疑理由

**禁止事项**：此阶段不允许修改任何文件。

### 3. 设计插桩方案

为每个可疑位置设计 console.log 插桩：

- **入口函数**：打印入参、调用时机
- **分支判断**：打印条件值、走的哪个分支
- **数据转换**：打印转换前后的值
- **异步操作**：打印 Promise 状态、返回值

插桩要求：
- 使用 `[DEBUG]` 前缀标记插桩日志，便于后续识别和移除
- 日志内容要有意义，不要只打印 `"here"`，要包含变量名和上下文
- 每个插桩点加一行注释说明为什么在这里插桩

示例：
```ts
console.log('[DEBUG] handleSubmit called', { formData, isValid })  // 怀疑表单数据未正确传递
```

### 4. 插桩并收集日志

1. 按方案插入 console.log
2. 告知用户：
   - 在哪些文件的哪些位置插了桩
   - 需要用户执行什么操作来复现问题
   - 请用户复现后将控制台输出贴回来

**⛔ 门禁 1：必须等待用户提供日志输出。禁止跳过、禁止假设日志内容。**

### 5. 分析日志并汇报

收到用户提供的控制台输出后：

1. 搜索 `[DEBUG]` 标记的日志行
2. 对比实际输出与预期：
   - 数据是否正确传递？
   - 分支走向是否符合预期？
   - 异步操作是否正常完成？
3. 缩小问题范围，定位根因
4. **向用户汇报分析结论**：
   - 日志中发现了什么
   - 推断的根因是什么
   - 准备怎么修

如果日志信息不足以定位，回到步骤 3 补充插桩点，再次收集。

**⛔ 门禁 2：必须等待用户确认根因分析。用户未确认前，禁止开始修改代码。**

### 6. 实施修复

用户确认根因后：

1. 实施修复（只改必要的代码）
2. **不要移除插桩代码**，保留 `[DEBUG]` 日志供验证
3. 告知用户：
   - 改了什么、为什么这么改
   - 请用户再次执行操作验证修复是否生效
   - 验证时观察控制台 `[DEBUG]` 日志，确认数据流是否符合预期

**⛔ 门禁 3：必须等待用户验证修复效果。禁止自动假设修复成功。**

### 7. 清理

用户确认修复生效后：

1. 移除所有 `[DEBUG]` 插桩代码（包括注释）
2. 告知用户清理完成

如果用户反馈修复无效或引入新问题，回到步骤 5 重新分析（保留插桩，补充新的插桩点）。

## 约束

- **信息收集优先**：禁止在步骤 4 之前修改业务逻辑代码
- **日志驱动**：步骤 5 的分析必须基于实际日志，不能凭空猜测
- **三次门禁**：步骤 4、5、6 各有一个硬性等待点，必须等用户反馈后才能继续
- **插桩保留到验证通过**：修复后保留插桩代码供用户验证，验证通过后才清理
- **最小改动**：修复时只改必要的代码，不做重构或优化
