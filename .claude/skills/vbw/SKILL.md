# VBW 工作流编排器

VBW（Vibe-Based Workflow）是一个插槽式工作流，将需求规划到开发验收拆为固定阶段，每个阶段可挂载不同 skill。

## 触发条件

通过 Skill 工具调用（`vbw`）。两种场景：
- **完整流程**：新功能开发，从阶段 1 开始
- **增量补充**：implement 阶段中途需要调整任务文档时，跳回 specify 补充

## 流程总览

```
explore → specify → implement → accept
  需求探索   需求产出   逐项开发   人工验收
```

specify 只产出骨架（README + task 文件），不强制深化所有细节。每个任务在 implement 阶段按需深化、开发、自检。验收不通过 → 回到 implement；需求变更 → 回到 explore。

## 核心纪律（不可绕过）

以下要素由编排层强制保证，任何外部 skill 都不能绕过：

1. **流程顺序**：必须按阶段顺序执行，不可跳过
2. **产出物规范**：
   - README 必须包含：需求标识、核心功能、任务列表
   - task 文件必须包含：depends（依赖声明）、验收清单、TODO
3. **质量门禁**：每个阶段产出物必须满足门禁条件才能进入下一阶段
4. **阶段转换确认**：每个阶段完成后必须暂停，向用户汇报阶段产出并询问以下问题，**用户明确确认后方可进入下一阶段**：
   - "是否有内容需要补充或调整？"
   - "是否进入阶段 N（<阶段名称>）？"
   - 用户未明确同意前，**禁止自动进入下一阶段**
5. **依赖解析**：执行任务前必须检查 depends，前置任务未完成不能开始
6. **循环机制**：验收不通过必须回到开发，需求变更必须回到探索

## 插槽解析规则

每个插槽在 `config.yaml` 中声明了 `skill` 和 `builtin` 两层：

```yaml
challenge:
  skill: grill-me      # 外部增强（可选）
  builtin: vbw/explore # 内置兜底（必有）
```

**执行顺序**：
1. 读取 `skill` 字段
2. 如果 `skill` 不为 null → 尝试调用该 skill
3. 如果 skill 未安装或调用失败 → 降级到 `builtin`
4. 如果 `skill` 为 null → 直接执行 `builtin`

**效果**：外部 skill 作为增强手段，有就用，没有就降级。核心流程始终可用。

## 阶段定义

### 阶段 1：需求探索（explore）

**目标**：明确要解决什么问题、涉及哪些模块、验收标准是什么。

**插槽**：`explore`（配置见 config.yaml）

**内置实现**（`vbw/explore`）：通过逐个提问梳理需求，每次只问一个问题。

**增强插槽**：`challenge` — 信息收集完成后，调用 challenge 插槽进行假设质疑。skill 为 null 时由 `vbw/explore` 内置质疑模式兜底。

**门禁条件**：
- [ ] 明确了要解决什么问题
- [ ] 明确了涉及哪些模块/页面
- [ ] 明确了验收标准（或标记为待深化）

**阶段转换**：门禁条件满足后，**必须暂停**，向用户汇报探索结果，询问"是否有内容需要补充或调整？是否进入阶段 2（需求产出）？"用户明确确认后方可进入。

### 阶段 2：需求产出（specify）

**目标**：生成 README.md + task 文件骨架。**只做骨架，不强制深化所有任务细节。**

**插槽**：`specify`

**内置实现**（`vbw/specify`）：
- 从分支名提取需求标识
- 创建 `docs/feature/` 目录和 README.md
- 填充核心功能概述
- 拆分任务（垂直切片优先），生成 task 文件
- task 的 TODO 可以是粗粒度的，待深化的内容写入"待解决"

**门禁条件**：
- [ ] README.md 包含需求标识（头部 `> 需求标识: ...`）
- [ ] README.md 包含核心功能、任务列表两个节
- [ ] 每个 task 文件包含 depends + 验收清单 + TODO
- [ ] 任务拆分符合垂直切片原则（每个任务是独立可验证的功能增量）
- [ ] 用户已确认拆分方案

**阶段转换**：门禁条件满足后，**必须暂停**，向用户汇报产出（README + task 文件列表），询问"是否有内容需要补充或调整？是否进入阶段 3（逐项开发）？"用户明确确认后方可进入。

### 阶段 3：逐项开发（implement）

**目标**：按任务列表逐个开发。**每个任务独立走深化 → 开发 → 自检循环。**

**插槽**：`implement`

**每个任务的执行流程**：

#### 3a. 定位与前置检查

1. 读取 README，找到第一个未完成的任务
2. 检查 depends — 前置任务未完成则提示用户
3. 检查"待解决" — 有待解决项则与用户逐一讨论，转化为 TODO 或已确定

#### 3b. 按需深化

**不强制所有任务都提前深化。** 开发当前任务时，根据需要深入讨论：

- **技术方案讨论**：涉及哪些文件？需要新建/修改哪些 domain、component、view？
- **边界条件梳理**：空数据、加载态、错误态如何处理？
- **验收标准细化**：怎么判断"做完了"？细化验收清单为具体用户可见场景
- **依赖与风险**：依赖哪些接口/数据？有哪些已知风险？
- **设计决策质疑**：读取 `config.yaml` 的 `challenge-design` 插槽。skill 不为 null 时调用外部 skill；为 null 时内置质疑 — "为什么不是另一种做法？"

深化结果写回 task 文件（待解决、已确定、验收清单、TODO）。

#### 3c. TDD 开发

按 TODO 列表逐项执行。**默认采用 TDD 流程**：

1. 对第一个未完成的 `- [ ]` 项，执行红-绿-重构循环：
   - 🔴 **Red**：先写一个描述预期行为的测试，运行确认它失败
   - 🟢 **Green**：写最少的代码让测试通过
   - 🔵 **Refactor**：优化代码结构，保持测试通过
   - 标记为 `[x]`
2. 继续下一项，直到全部完成

**TDD 豁免**：TODO 项可标记 `[no-tdd]` 跳过测试（如纯 UI 样式调整、配置变更、文档更新）。未标记的默认走 TDD。

**代码搜索**：查找已有模块、组件、接口时，优先使用 CodeGraph；不可用时回退到 Grep/Glob/Read。

开发过程中：
- **禁止自动 commit**，所有提交由用户手动控制
- 可调整 TODO 列表
- 遇到新问题可添加到待解决

**动态拆分子任务**：开发中发现需要拆分子任务时：
1. 新建 `<父slug>-<子slug>.md`（使用完整 task 模板）
2. 按需声明 depends
3. README 不必改动（除非新任务是大节点，需用户确认后加入 README）

#### 3d. 自检

所有 TODO 完成后：

**第一层：自检**（当前 agent 快速过一遍）

- [ ] 所有 TODO 项已标记 `[x]`
- [ ] 待解决已清空或全部转化为已确定
- [ ] 符合 `.claude/rules/code-reviews.md` 清单：
  - [ ] models 是纯函数（无 `this`、无响应式 API）
  - [ ] 常量已收拢到 `constants.ts` 并加了 `as const`
  - [ ] 表单场景：`formData` 不含 UI 属性（UI 属性已放 `uiContext`）
  - [ ] 视图模板：无复杂表达式（如 `v-if="a && b"`）
  - [ ] 视图模板：无可选链防御链（如 `data?.xxx`）

**第二层：交叉审查**（启动新 agent，干净上下文）

自检通过后，启动一个新的 agent 进行交叉审查：
- 注入干净上下文（无开发过程的历史对话）
- 提供 coding 规范（`.claude/rules/domains-code.md`、`.claude/rules/views.md`、`.claude/rules/code-reviews.md`）和本轮变更的文件列表
- 新 agent 处于"聪明区"，能发现因上下文疲劳而忽略的边缘 Bug
- 审查结果：通过 → 继续；有问题 → 修复后重新自检

#### 3e. 用户验收

读取当前任务的**验收清单**，逐项引导用户核验：

1. 展示验收清单（每项为 `- [ ]` 格式）
2. 用户逐项确认或反馈问题
3. 通过的项目标记为 `[x]`
4. 未通过的项目记录问题，回到 3c 修复

验收循环：
- 用户发现问题 → 调用 debug 插槽诊断 → 基于诊断结果修复 → 重新展示相关验收项
  - 读取 `config.yaml` 的 `debug` 插槽。skill 不为 null 时调用外部 skill；为 null 时执行 `vbw/debug` 内置诊断
  - 诊断流程：先插桩收集运行时日志，再基于日志定位根因，最后修复
  - **禁止跳过诊断直接改代码**
- 所有验收项通过 → 更新 README 标记任务完成，继续下一个任务

**重要**：验收以清单为准，不能跳过或笼统确认。

#### 3f. 循环

- **还有未完成任务**：回到 3a，继续下一个任务
- **所有任务完成**：进入阶段 4

**暂停条件**：出现以下情况时，暂停开发，回到 specify 补充任务文档：
- 需要新增大节点 task（改 README 任务列表 + 新建 task 文件）
- 当前 task 拆分不合理，需要拆分或合并
- 需求本身发生变化（背景、核心功能、验收标准）

**门禁条件**（单个任务完成的标准）：
- [ ] 所有 TODO 项标记 `[x]`
- [ ] 待解决已清空或全部转化为已确定
- [ ] 自检 + 交叉审查通过
- [ ] 用户逐项验收通过

**阶段转换**：所有任务完成、门禁条件满足后，**必须暂停**，向用户汇报开发成果摘要（完成了哪些任务），询问"是否进入阶段 4（收尾）？"用户明确确认后方可进入。

### 阶段 4：收尾（accept）

**目标**：需求级一致性检查，填写总结。

**插槽**：`accept`（不可配置）

**流程**：

1. **需求级一致性检查**：
   - [ ] 每个 task 的已确定内容与实际代码一致
   - [ ] README 描述的核心功能全部被任务覆盖

2. **填写总结**：在 README.md 的总结区域填写成果提炼
   - 实现了什么功能
   - 关键技术决策
   - 值得注意的问题或发现

   **注意：总结是成果提炼，不是 git log 副本。**

3. 告知用户开发完成

## 循环机制

```
验收不通过 ──→ 回到 implement（阶段 3）修复当前任务
需求变更   ──→ 回到 explore（阶段 1）
新发现任务 ──→ 回到 specify（阶段 2）补充 task 文件
```
