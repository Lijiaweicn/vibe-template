# VBW 工作流编排器

VBW（Vibe-Based Workflow）是一个插槽式工作流，将需求规划到开发验收拆为固定阶段，每个阶段可挂载不同 skill。

## 触发条件

通过 Skill 工具调用（`vbw`）。两种场景：
- **完整流程**：新功能开发，从阶段 1 开始
- **增量补充**：implement 阶段中途需要调整任务文档时，跳到阶段 3

## 流程总览

```
explore → specify → validate → implement → review → accept
  需求探索   需求产出   任务深化   逐项开发   代码审查   人工验收
```

每个阶段有**门禁条件**，不通过不能进入下一阶段。验收不通过 → 回到 implement；需求变更 → 回到 explore。

## 核心纪律（不可绕过）

以下要素由编排层强制保证，任何外部 skill 都不能绕过：

1. **流程顺序**：必须按阶段顺序执行，不可跳过
2. **产出物规范**：
   - README 必须包含：需求标识、需求背景、核心功能、任务列表
   - task 文件必须包含：depends（依赖声明）、验收清单、TODO
3. **质量门禁**：每个阶段产出物必须满足门禁条件才能进入下一阶段
4. **依赖解析**：执行任务前必须检查 depends，前置任务未完成不能开始
5. **循环机制**：验收不通过必须回到开发，需求变更必须回到探索

## 插槽解析规则

每个插槽在 `config.yaml` 中声明了 `skill` 和 `builtin` 两层：

```yaml
challenge:
  skill: grill-me      # 外部增强（可选）
  builtin: vbw/explore # 内置兜底（必有）
```

**执行顺序**：
1. 读取 `skill` 字段
2. 如果 `skill` 不为 null → 尝试调用该 skill
3. 如果 skill 未安装或调用失败 → 降级到 `builtin`
4. 如果 `skill` 为 null → 直接执行 `builtin`

**效果**：外部 skill 作为增强手段，有就用，没有就降级。核心流程始终可用。

## 阶段定义

### 阶段 1：需求探索（explore）

**目标**：明确要解决什么问题、涉及哪些模块、验收标准是什么。

**插槽**：`explore`（配置见 config.yaml）

**内置实现**（`vbw/explore`）：通过逐个提问梳理需求，每次只问一个问题。

**增强插槽**：`challenge` — 信息收集完成后，调用 challenge 插槽进行假设质疑。skill 为 null 时由 `vbw/explore` 内置质疑模式兜底。

**门禁条件**：
- [ ] 明确了要解决什么问题
- [ ] 明确了涉及哪些模块/页面
- [ ] 明确了验收标准（或标记为待深化）

### 阶段 2：需求产出（specify）

**目标**：生成 README.md + task 文件骨架。

**插槽**：`specify`

**内置实现**（`vbw/specify`）：
- 从分支名提取需求标识
- 创建 `docs/feature/` 目录和 README.md
- 填充需求背景和核心功能
- 拆分任务（垂直切片优先），生成 task 文件

**门禁条件**：
- [ ] README.md 包含需求标识（头部 `> 需求标识: ...`）
- [ ] README.md 包含需求背景、核心功能、任务列表三个节
- [ ] 每个 task 文件包含 depends + 验收清单 + TODO
- [ ] 任务拆分符合垂直切片原则（每个任务是独立可验证的功能增量）

### 阶段 3：任务深化（validate）

**目标**：深化讨论每个任务，交叉验证需求覆盖度。

**插槽**：`validate`

**增强插槽**：`challenge-design` — 深化讨论中触发设计决策质疑。skill 为 null 时由 `vbw/validate` 内置质疑维度兜底。

**内置实现**（`vbw/validate`）：
- 逐任务深入讨论（技术方案、边界条件、验收标准、依赖与风险）
- 交叉验证（需求覆盖度、任务间一致性、规范对齐、完整性）
- 就绪检查

**门禁条件**：
- [ ] 每个 task 的 TODO 可以直接指导编码（不能只有笼统描述）
- [ ] 每个 task 的验收清单具体可执行（必须是用户可见场景）
- [ ] 需求覆盖度 100%（README 的每个需求点都有对应 task）
- [ ] 无循环依赖、无任务间逻辑冲突
- [ ] 待解决项不会阻塞开发（阻塞项必须在进入 implement 前解决）

### 阶段 4：逐项开发（implement）

**目标**：按 TODO 列表驱动开发，逐项完成。

**插槽**：`implement`

**增强插槽**：`tdd` — 逐项开发中触发 TDD 流程。skill 为 null 时由 `vbw/implement` 内置 TDD 兜底。

**内置实现**（`vbw/implement`）：
- 定位第一个未完成任务
- 检查依赖 → 检查待解决 → 逐项开发
- 开发过程中禁止自动 commit
- 支持动态拆分子任务

**门禁条件**：
- [ ] 所有 TODO 项标记 `[x]`
- [ ] 待解决已清空或全部转化为已确定

### 阶段 5：代码审查（review）

**目标**：验证代码质量和规范对齐。

**插槽**：`review`

**内置实现**（`vbw/review`）：自检清单（来自 workflow.md）：
- models 是纯函数
- 常量已收拢到 `constants.ts` 并加了 `as const`
- 表单场景：`formData` 不含 UI 属性
- 视图模板：无复杂表达式、无可选链防御链

**门禁条件**：
- [ ] Code Review 清单全部通过

### 阶段 6：人工验收（accept）

**目标**：用户逐项确认验收清单。

**此阶段不可配置，固定使用 `vbw/accept` 的验收流程。**

**流程**：
1. 展示验收清单（每项为 `- [ ]` 格式）
2. 用户逐项确认或反馈问题
3. 通过的项目标记为 `- [x]`
4. 未通过的项目记录问题，回到阶段 4（implement）修复

**门禁条件**：
- [ ] 用户逐项确认验收清单，全部 `[x]`

## 上下文管理

LLM 在上下文较少时最聪明（"聪明区"），随着 token 增加注意力会被拉伸，决策质量下降。VBW 通过以下机制管理上下文：

**阶段间重置提示**：每个阶段完成后，输出提示：

> 当前阶段完成。建议清空上下文后再进入下一阶段，以保持 AI 处于"聪明区"。

**关键重置点**（强烈建议）：
- **implement → review**：写代码的上下文和审查代码的上下文必须分开。写代码的 agent 会因"确认偏见"忽略自己的错误
- **review → accept**：审查上下文和验收上下文分开，确保验收时有 fresh eyes

**不自动清空**（清空是破坏性操作），只提示用户手动执行。用户可选择忽略（如阶段间上下文确实不长时）。

## 循环机制

```
验收不通过 ──→ 回到 implement（阶段 4）
需求变更   ──→ 回到 explore（阶段 1）
新发现任务 ──→ 回到 specify（阶段 2）补充 task 文件
```

## 收尾

所有任务验收通过后：
1. 更新 README.md 的总结区域
2. 需求级一致性检查（已确定内容与实际代码一致、需求全部被任务覆盖）
3. 告知用户开发完成
