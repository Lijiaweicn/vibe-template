# VBW 需求规划

通过 AI 辅助访谈梳理需求，生成需求文档和任务拆分。

## 触发条件

通过 Skill 工具调用（`vbw-plan`）。两种场景：
- **初始规划**：新功能开发时由 CLAUDE.md 引导调用，执行完整流程（步骤 1-10）
- **增量补充**：vbw-dev 开发过程中发现需要调整任务文档时调用，只处理变更部分（步骤 5-9），跳过已完成的访谈和创建步骤

## 流程

### 1. 需求访谈

通过提问梳理需求，每次只问一个问题：

- 这个需求要解决什么问题？
- 涉及哪些模块/页面？
- 有没有参考的设计稿或接口文档？
- 有哪些已知的约束或限制？
- 预期的验收标准是什么？

### 2. 提取需求标识

从当前分支名提取需求标识（去掉 `feature/`、`fix/` 等前缀），用于 README 标题和 task 文件命名。

**将需求标识写入 README 头部**，供 vbw-dev 直接读取，无需重新解析分支名。

### 3. 创建目录和文件

用 Write 工具在 `docs/feature/` 目录创建文件：

**README.md**：

```markdown
# <需求标识或功能名称>

> 需求标识: `<从分支名提取的标识>`

## 需求背景
<!-- 为什么做、解决什么问题 -->

## 核心功能
<!-- 概述性描述，不超过几条 -->

## 任务列表
<!-- 大任务节点，链接到 task 文件 -->
- [ ] [slug-1](slug-1.md)
- [ ] [slug-2](slug-2.md)

## 总结
<!-- 开发完成后填写成果提炼 -->
```

**注意**：task 文件链接格式为 `[slug](slug.md)`，实际文件名即 `slug.md`。

### 4. 填充 README

根据访谈结果填充：
- 需求背景：为什么要做
- 核心功能：概述性描述，不超过几条

### 5. 拆分任务

根据需求内容拆分任务。

**任务分层标准**：

判断依据：用户能否单独验收这个节点。

| 是大节点（README 层） | 是子任务（task 内拆分） |
|---|---|
| 登录表单 — 用户能看到完整的登录功能 | 验证码组件 — 用户不单独验收它 |
| 列表筛选 — 用户能操作筛选功能 | 筛选参数序列化 — 实现细节 |
| 报价保存 — 用户能保存并看到结果 | domain 模型构建 — 底层步骤 |

大节点出现在 README 的任务列表中，子任务仅在 task 文件内声明或开发中动态产生。

**拆分原则：垂直切片优先**

每个大任务节点是一个**独立可验证的用户可见功能增量**，做完即可独立验证。

| 正确（垂直切，按功能） | 错误（水平切，按技术层） |
|---|---|
| 报价表单 - 基础字段录入与保存 | 建立报价表单 domain 模型 |
| 报价表单 - 大客户特殊定价显隐 | 开发报价表单 UI 视图 |
| 报价列表 - 筛选与排序 | 写报价表单测试 |

**凝聚度检查**：

- **独立可验证**：做完这个任务，用户/QA 能看到一个完整的功能点
- **纵向穿透**：涉及该功能所需的全部层（domain → view → test），但不涉及其他功能
- **禁止按技术层拆分**：不要把"写 model"和"写 view"分成两个大节点
- **功能不跨任务**：如果一个功能做完后才能看到效果，它们应该合并；如果 Todo 超过 10 项，考虑拆出子任务

**任务文件命名**：用 slug 命名，文件名即 ID。

**slug 定义**：小写英文单词用短横线连接，如 `login-form`、`api-auth`、`forgot-password`。禁止中文、驼峰、空格。

生成 `<slug>.md` 文件，如 `login-form.md`。

**任务依赖声明**：每个 task 文件头部用 frontmatter 声明依赖：

```markdown
---
depends: [前置任务slug1, 前置任务slug2]
---
```

无依赖时省略 frontmatter 或写 `depends: []`。

**task 文件模板**：

```markdown
---
depends: []
---
# <任务目标>
<!-- 一句话：这个任务要达成什么效果 -->

## 待解决
<!-- 阻塞项：未想通的技术方案、未确认的外部依赖等 -->
<!-- 无则留空或删除此节 -->

## 已确定
<!-- 已敲定的决策、接口、数据结构 -->

## TODO
- [ ] 步骤1
- [ ] 步骤2

## 验收清单
- [ ] 可观测的用户行为1
- [ ] 可观测的用户行为2
```

**验收清单**：每个任务必须包含验收清单，列出用户可在页面上逐一核验的具体行为：
- 格式为 `- [ ] 验收项描述`，描述须是可观察的用户可见行为
- 禁止笼统描述（如"功能正常"），必须是具体场景（如"输入非法邮箱后点击保存，显示红色错误提示"）
- 覆盖核心路径、边界情况和异常场景

### 6. 用户确认

展示拆分方案，用户可调整：
- 合并/拆分任务
- 调整 Todo 步骤
- 补充待解决内容

### 7. 深化讨论

**此阶段是必经步骤，不可跳过。** 在基础骨架确认后，对每个任务逐一深入讨论：

**逐任务深入**（每个任务一次性覆盖以下 4 个维度，减少往返）：

1. **技术方案讨论**：这个任务涉及哪些文件？需要新建/修改哪些 domain、component、view？
2. **边界条件梳理**：有哪些边界情况和异常场景？空数据、加载态、错误态如何处理？
3. **验收标准细化**：怎么判断这个任务"做完了"？有哪些具体的验收点？产出为任务文件的**验收清单**，每条必须是可以观察的用户可见行为
4. **依赖与风险**：这个任务依赖哪些接口/数据？有哪些已知风险？

**产出**：更新每个 task 文件的以下字段：
- **待解决** → 补充从深化讨论中发现的阻塞项
- **已确定** → 补充已敲定的决策、接口、数据结构
- **验收清单** → 按步骤 5 的要求细化具体验收点
- **Todo** → 细化步骤，使其可以直接指导编码

**重要**：深化讨论中发现的新问题、新风险，必须写回 task 文件，不能仅停留在对话中。

### 8. 交叉验证

**此阶段是必经步骤，不可跳过。** 从多个维度交叉检查所有任务文档：

**A. 需求覆盖度检查**：
- 逐条对照 README 的需求背景和核心功能，确认每个需求点都有对应的任务覆盖
- 标记遗漏的需求点，补充到对应任务或新建任务

**B. 任务间一致性检查**：
- 检查任务之间的依赖关系是否合理（A 的输出是否是 B 的输入？顺序是否正确？）
- 检查是否有逻辑冲突（两个任务修改同一个文件？设计决策不一致？）
- 检查是否有重复工作（两个任务做了类似的事？）
- **重点检查凝聚度**：是否有功能被错误地分散到多个大节点中？如有，立即合并

**C. 项目规范对齐检查**（规则文件已在上下文中自动加载，直接引用检查，无需重新读取）：
- 对照 `coding.md` 检查：涉及后端接口/领域建模的业务代码是否符合分层规范（domain → scene → view）？非业务代码（工具函数、配置等）不在此检查范围
- 对照 `view.md` 检查：视图层是否有业务逻辑泄漏风险？
- 对照 `testing.md` 检查：P0 优先级的逻辑是否标记了测试要求？
- 对照 `project.md` 检查：是否有历史遗留坑点需要注意？

**D. 完整性检查**：
- 每个 task 的 Todo 列表是否可以直接指导编码？（不能只有"开发XX功能"这种笼统描述）
- 每个 task 的验收清单是否具体可执行？（不能只有"功能正常"，必须是具体的用户可见场景）
- 每个 task 的待解决是否可能阻塞开发？（阻塞项必须在进入 dev 前解决）
- 是否有遗漏的异常处理、空态、加载态？

**产出**：更新 task 文件，修正发现的问题。如果发现重大遗漏或冲突，回到步骤 5 调整任务拆分。

### 9. 就绪检查清单

**汇总确认，所有项通过后规划阶段才算完成：**

- [ ] README 头部包含需求标识
- [ ] 步骤 8 的交叉验证已执行，发现的问题已修正
- [ ] 所有 task 文件内容已更新（深化讨论和交叉验证的产出已写回）

**所有项通过后，向用户展示就绪检查清单结果，等待用户最终确认。**

### 10. 输出

告知用户规划阶段完成，所有文档已就绪。

> 规划阶段完成。所有 task 文档已就绪，就绪检查清单全部通过。
> 当你准备好开始编码时，执行 vbw-dev 开始第一个任务。
