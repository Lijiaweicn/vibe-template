# VBW 需求规划

通过 AI 辅助访谈梳理需求，生成需求文档和任务拆分。

## 触发条件

通过 Skill 工具调用（`vbw-plan`）。用户在新功能开发时由 CLAUDE.md 引导调用。

## 流程

### 1. 判断模式

根据需求描述的复杂度判断使用哪种模式：

- **完整流程**：需求涉及多模块、需要设计决策、预期任务 >= 3 个
- **快速通道**：需求简单明确、改动范围小、预期任务 < 3 个

如果不确定，询问用户选择。

### 2A. 完整流程

#### 2A.1 需求访谈

通过提问梳理需求，每次只问一个问题：

- 这个需求要解决什么问题？
- 涉及哪些模块/页面？
- 有没有参考的设计稿或接口文档？
- 有哪些已知的约束或限制？
- 预期的验收标准是什么？

#### 2A.2 创建目录和文件

从当前分支名提取需求标识（去掉 `feature/`、`fix/` 等前缀），然后用 Write 工具创建以下文件：

**目录**：`docs/<需求标识>/`

**README.md**：

```markdown
# <需求标识>

## 概览
<!-- 一句话描述本次需求的目标 -->

## 需求资源
- [需求文档](prd.md)

## 任务列表
<!-- < 3 个任务：直接在此编写任务内容 -->
<!-- >= 3 个任务：用引用格式 -->

## 总结
<!-- 开发完成后填写成果提炼 -->
```

**prd.md**：

```markdown
# 需求文档

## 需求背景
<!-- 为什么要做这个需求 -->

## 需求描述
<!-- 具体要做什么 -->

## 需求链接
<!-- 相关链接、设计稿、接口文档等 -->
```

#### 2A.3 填充 prd.md

根据访谈结果填充 prd.md：
- 需求背景：为什么要做
- 需求描述：具体做什么
- 需求链接：相关资源

#### 2A.4 拆分任务

根据 prd 内容拆分任务。**必须遵循以下拆分原则：**

**拆分原则：垂直切片优先**

每个任务是一个**独立可验证的用户可见功能增量**，做完即可独立验证。

| 正确（垂直切，按功能） | 错误（水平切，按技术层） |
|---|---|
| task-1: 报价表单 - 基础字段录入与保存 | task-1: 建立报价表单 domain 模型 |
| task-2: 报价表单 - 大客户特殊定价显隐 | task-2: 开发报价表单 UI 视图 |
| task-3: 报价列表 - 筛选与排序 | task-3: 写报价表单测试 |

**凝聚度检查**：

- **独立可验证**：做完这个任务，用户/QA 能看到一个完整的功能点
- **纵向穿透**：涉及该功能所需的全部层（domain → view → test），但不涉及其他功能
- **禁止按技术层拆分**：不要把"写 model"和"写 view"分成两个任务
- **功能不跨任务**：如果一个功能做完后才能看到效果，它们应该合并；如果 Todo 超过 10 项，考虑再拆

**唯一例外**：底层模型被多个上层功能共享且模型本身足够复杂时，可以单独拆出，但必须自带测试验证其正确性。

**任务数量判断**：

**任务数 < 3**：直接在 README.md 的任务列表区域编写，每个任务包含：
- 任务目标
- 待确认/待解决/已确认/限制（按需）
- 验收清单
- Todo 列表

**任务数 >= 3**：生成 `task-N-标题.md` 文件，每个文件包含：
- 任务目标
- 待确认
- 待解决
- 已确认
- 限制
- 验收清单
- Todo 列表

**验收清单**：每个任务必须包含验收清单，列出用户可在页面上逐一核验的具体行为：
- 格式为 `- [ ] 验收项描述`，描述须是可观察的用户可见行为
- 禁止笼统描述（如"功能正常"），必须是具体场景（如"输入非法邮箱后点击保存，显示红色错误提示"）
- 覆盖核心路径、边界情况和异常场景

README.md 中用引用格式列出任务。

#### 2A.5 用户确认

展示拆分方案，用户可调整：
- 合并/拆分任务
- 调整 Todo 步骤
- 补充待确认/限制内容

#### 2A.6 深化讨论

**此阶段是必经步骤，不可跳过。** 在基础骨架确认后，对每个任务逐一深入讨论：

**逐任务深入**（每个任务一次性覆盖以下 4 个维度，减少往返）：

1. **技术方案讨论**：这个任务涉及哪些文件？需要新建/修改哪些 domain、component、view？
2. **边界条件梳理**：有哪些边界情况和异常场景？空数据、加载态、错误态如何处理？
3. **验收标准细化**：怎么判断这个任务"做完了"？有哪些具体的验收点？产出为任务文件的**验收清单**，每条必须是可以观察的用户可见行为
4. **依赖与风险**：这个任务依赖哪些接口/数据？有哪些已知风险？

**产出**：更新每个 task 文件的以下字段：
- **待确认** → 补充从深化讨论中发现的新问题
- **待解决** → 补充需要提前调研的技术问题
- **限制** → 补充技术约束和边界条件
- **验收清单** → 将验收标准具体化为可逐项核验的 checklist
- **Todo** → 细化步骤，使其可以直接指导编码

**重要**：深化讨论中发现的新问题、新风险，必须写回 task 文件，不能仅停留在对话中。

#### 2A.7 交叉验证

**此阶段是必经步骤，不可跳过。** 从多个维度交叉检查所有任务文档：

**A. 需求覆盖度检查**：
- 逐条对照 prd.md 的需求描述，确认每个需求点都有对应的任务覆盖
- 标记遗漏的需求点，补充到对应任务或新建任务

**B. 任务间一致性检查**：
- 检查任务之间的依赖关系是否合理（A 的输出是否是 B 的输入？顺序是否正确？）
- 检查是否有逻辑冲突（两个任务修改同一个文件？设计决策不一致？）
- 检查是否有重复工作（两个任务做了类似的事？）
- **重点检查凝聚度**：是否有功能被错误地分散到多个任务中？如有，立即合并

**C. 项目规范对齐检查**（规则文件已在上下文中自动加载，直接引用检查，无需重新读取）：
- 对照 `coding.md` 检查：任务涉及的文件是否符合分层规范（domain → scene → view）？
- 对照 `view.md` 检查：视图层是否有业务逻辑泄漏风险？
- 对照 `testing.md` 检查：P0 优先级的逻辑是否标记了测试要求？
- 对照 `project.md` 检查：是否有历史遗留坑点需要注意？

**D. 完整性检查**：
- 每个 task 的 Todo 列表是否可以直接指导编码？（不能只有"开发XX功能"这种笼统描述）
- 每个 task 的验收清单是否具体可执行？（不能只有"功能正常"，必须是具体的用户可见场景）
- 每个 task 的待确认/待解决是否可能阻塞开发？（阻塞项必须在进入 dev 前解决）
- 是否有遗漏的异常处理、空态、加载态？

**产出**：更新 task 文件，修正发现的问题。如果发现重大遗漏或冲突，回到步骤 2A.4 调整任务拆分。

#### 2A.8 就绪检查清单

**所有任务通过以下检查后，规划阶段才算完成：**

- [ ] 每个 task 的 Todo 列表足够具体，可直接指导编码
- [ ] 每个 task 的验收清单已编写，验收项具体可执行（用户可见行为，非笼统描述）
- [ ] 每个 task 的阻塞项（待确认/待解决）已清空或降级为非阻塞
- [ ] 需求覆盖度检查通过（prd.md 的每个需求点都有任务对应）
- [ ] 任务间一致性检查通过（无冲突、无遗漏、依赖合理、凝聚度达标）
- [ ] 项目规范对齐检查通过（符合 coding.md / testing.md / view.md / project.md）
- [ ] 所有 task 文件内容已更新（深化讨论和交叉验证的产出已写回）

**所有项通过后，向用户展示就绪检查清单结果，等待用户最终确认。**

### 2B. 快速通道

#### 2B.1 创建目录和文件

从当前分支名提取需求标识（去掉 `feature/`、`fix/` 等前缀），然后用 Write 工具创建：

**目录**：`docs/<需求标识>/`

**README.md**：

```markdown
# <需求标识>

## 概览
<!-- 一句话描述本次需求的目标 -->

## 需求描述
<!-- 简要背景和具体内容 -->

## 任务列表
<!-- 内联任务，每个任务用 ### 标题 + Todo 列表 -->

## 总结
<!-- 开发完成后填写成果提炼 -->
```

#### 2B.2 填充 README.md

在 README.md 中直接编写：
- 概览：一句话目标
- 需求描述：简要背景和内容
- 任务列表：内联 Todo 任务（### 任务N + Todo 列表）

任务拆分的凝聚度检查同样适用于快速通道——每个任务应是一个独立可验证的功能增量，禁止按技术层拆分。

#### 2B.3 用户确认及就绪检查

展示内容，确认以下检查项通过后才能进入开发：

- [ ] 需求描述完整（背景 + 内容 + 边界条件）
- [ ] Todo 步骤可直接指导编码，不是笼统描述
- [ ] 每个任务有验收清单，验收项具体可执行
- [ ] 任务符合垂直切片原则，功能内聚
- [ ] 符合项目编码规范（coding.md / testing.md / project.md）

用户确认通过后即完成规划。

### 3. 输出

告知用户规划阶段完成，所有文档已就绪。

> 规划阶段完成。所有 task 文档已就绪，就绪检查清单全部通过。
> 当你准备好开始编码时，执行 vbw-dev 开始第一个任务。
