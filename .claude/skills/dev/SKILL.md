# /dev — 新功能开发

## 命令格式

```
/dev                            ← 从 issue 列表选取或输入新需求
/dev issue-062301               ← 指定 issue 开发
```

## When to Use

- 从 issue 列表选取需求进行开发
- 用户明确说"开发 xxx"、"实现 xxx"
- 需要实现一个新功能或对已有功能做显著改动

## When NOT to Use

- 只是想记录需求 → 用 `/issue`
- 修复已有功能的 bug → 用 `/fix`
- 只是想了解代码或做技术调研 → 直接对话
- 单行修复、typo 修正 → 直接改，不需要走流程

## 文档流转

一份文档贯穿整个生命周期：

```
docs/issue/issue-062301-xxx.md     (status: open)
        ↓ 启动 dev
docs/plan/issue-062301-xxx.md      (status: dev)
        ↓ 开发完成
docs/archive/2026/issue-062301-xxx.md  (status: archive)
```

**状态流转：** `open -> dev -> archive`

## 目录结构

```
docs/plan/
├── issue-062301-xxx.md    ← 需求文档（从 issue 移入）
├── 任务1.md               ← 任务文件（临时）
└── 任务2.md               ← 任务文件（临时）
```

## 任务文件模板

任务文件是临时工作文档，不需要 frontmatter：

```markdown
# 任务标题

## 技术方案

- 功能归属：放在哪个包/模块
- 依赖关系：依赖哪些模块
- 接口设计：API 接口、数据结构
- 技术选型：使用哪些技术/库

## TODO

- [ ] 执行步骤 1
- [ ] 执行步骤 2

## 验收清单

- [ ] 功能点 1
- [ ] 功能点 2
```

## 流程

### 启动

1. 检查 `docs/plan/` 是否已有进行中的需求（status: dev 的文件）
   - **有** → 进入「进度恢复」
   - **无** → 检查 `docs/issue/` 是否有需求列表
     - **有需求** → 列出待开发需求（标题 + priority + summary），让用户选取或输入新需求
     - **无需求** → 提示用户输入需求描述（或先 `/issue` 捕获）
2. 如果从 issue 列表选取：
   - 移动文件到 `docs/plan/`
   - 更新 status 为 dev
   - 更新 `docs/issue/README.md` 索引
3. **等待用户明确指令**

### 进度恢复（启动时）

1. 读取需求文档和任务文件
2. 总结当前进度（已完成/进行中/待开始的任务）
3. 向用户汇报，给出下一步建议
4. **等待用户明确指令**

### 需求理解

**信息收集**：

- 扫描项目结构（优先使用 codegraph，未安装时提示用户可选安装，回退到 Grep/Read）
  - 识别包/模块入口，获取导出列表
  - 识别页面目录、状态管理等关键结构
- 需求模糊时，逐项确认深入提问

**假设质疑**（信息收集完成后）：

- 对需求的每个方面持续追问，直到与用户达成共识
- 沿着决策树的每个分支深入，逐个解决依赖关系
- 每个问题给出推荐答案，让用户做选择题而非填空题
- 一次只问一个问题，避免信息过载
- 能从代码库找到答案的，自己探索后向用户确认

**产出**：在需求文档中增加「任务列表」章节
**⏸ 等待用户确认后再进入任务规划**

### 任务规划

**YAGNI 检查**（创建任务前，逐项审视）：

1. **需要存在吗？** 这个功能/模块是否是当前需求明确要求的？推测性需求 → 跳过
2. **已有吗？** 项目中是否已有类似实现可以复用？不要重新发明轮子
3. **标准库能做到吗？** 是否有内置方案或已安装依赖能解决？
4. **一行能搞定吗？** 能用简单方案解决就不用复杂方案

被淘汰的任务记录淘汰原因到需求文档，便于后续回顾。

- **创建任务文件**：为每个任务创建独立的 md 文件
- **更新任务列表**：在需求文档中添加任务链接
- 如需拆分任务，先与用户确认
- **快速验证建议**：技术方案涉及以下情况时，主动建议在任务列表最前面插入一个 demo/POC 验证任务：
  - 引入新的第三方库/工具
  - 使用项目中没有先例的模式
  - 涉及跨包协作的新路径
  - 技术方案有多个候选需要验证
  - 用户也可以随时要求加 demo 任务
- **⏸ 等待用户确认后再进入开发**

### 开发执行

按 TODO 列表逐项执行。

#### TDD 适用范围

TDD 适用于**无副作用的 TS 代码**：

| 适用 TDD | 不适用 TDD |
|----------|-----------|
| 纯函数、工具函数 | Vue/React 组件渲染 |
| 业务逻辑、数据转换 | 样式、布局调整 |
| 领域模型、状态计算 | 配置变更 |
| service 编排（mock 依赖） | 文档更新 |
| 校验规则、权限判断 | 基础设施胶水代码 |
| | 后端接口请求代码（API 调用、请求配置） |

判断标准：这段代码能否在不依赖 DOM、网络、文件系统的情况下独立验证？能 → TDD。

#### TDD 开发（红-绿-重构）

对第一个未完成的 `- [ ]` 项，如果是适用 TDD 的代码，执行红-绿-重构循环：

1. 🔴 **Red**：先写一个描述预期行为的测试，运行确认它失败
2. 🟢 **Green**：写最少的代码让测试通过
3. 🔵 **Refactor**：优化代码结构，保持测试通过
4. 标记为 `[x]`，继续下一项

不适用 TDD 的 TODO 项，直接实现后标记 `[x]`。

#### 开发纪律

- 全部 TODO 完成后，执行 `pnpm lint` + `pnpm check`，修复问题直到通过
- **禁止自动 commit**，所有提交由用户手动控制
- **范围控制**：开发过程中发现的新任务或新需求，提醒用户 `/issue` 记录，不加入当前任务列表
- **动态拆分**：开发中发现需要拆分子任务时，新建 `<父slug>-<子slug>.md`，按需声明依赖

### 代码审查（每个任务完成后，可选）

如果项目配置了 code-reviewer agent（`.claude/agents/code-reviewer.md`），自动触发审查：

1. 调用 code-reviewer agent，传入当前任务变更的文件
2. 审查结果处理：
   - blocker → 必须修复后才能继续
   - risk → 评估后决定是否修复
   - improvement → 记录，可后续处理
   - uncertain → 提交用户确认
3. 修复后重新执行 `pnpm lint` + `pnpm check`

如果未配置 code-reviewer，跳过自动审查，直接进入验收。

审查通过后，向用户汇报当前任务完成情况，列出验收清单内容供用户逐项确认。
**⏸ 等待用户验证功能实现** — 用户确认后标记验收清单，进入下一个任务或需求归档

### 需求归档（所有任务完成 + 用户确认后）

1. **写开发总结**：在需求文档中增加「开发总结」章节（没有的内容不要编造）：
   - 功能增量：新增/修改了哪些功能
   - 决策记录：技术决策及原因（如有）
2. **更新验收标准**：标记为 `[x]`
3. **删除任务文件**：`docs/plan/` 下所有子任务 `.md` 文件是临时工作文档，归档前必须删除
4. **移动需求文档**：将需求文档（仅主文档）移动到 `docs/archive/{year}/`
5. **更新状态**：将 status 更新为 archive
6. **更新索引**：更新 `docs/issue/README.md`（如有对应 issue）

## Anti-Rationalizations

| Agent 的借口 | 反驳 |
|-------------|------|
| "先写代码，测试之后补" | 没有测试的代码是猜测，不是实现。红-绿-重构的第一步是 Red |
| "这个太简单不需要测试" | 适用 TDD 的代码，越简单越该测——测试成本低，漏掉的代价高 |
| "改动很小不用走流程" | 小改动也能引入大 bug，流程保护的是你不是在浪费时间 |
| "我先跳过任务规划直接写" | 没有规划的开发是盲目探索，边写边改比先想清楚更慢 |
| "这个需求很清楚不需要确认" | 你以为清楚 ≠ 用户觉得清楚，确认成本远低于返工成本 |
| "加个 if 就能搞定" | 治标不治本，同类问题会再出现 |

## Red Flags

- TODO 项超过 10 个 → 考虑拆分需求或合并细碎任务
- 单个任务文件超过 200 行 → 考虑拆分子任务
- 连续 3 个任务都判定为"不适用 TDD" → 审查判定是否合理，是否在逃避测试
- 开发过程中频繁修改任务文件 → 需求理解不充分，暂停并重新确认
- 一个任务的代码改动超过 300 行 → 考虑拆分为更小的增量
- YAGNI 检查连续放行 5 个以上任务 → 审查是否对"需要存在"过于宽松
