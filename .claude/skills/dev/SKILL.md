# /dev — 新功能开发

## 命令格式

```
/dev
```

一个分支一个需求，docs/plan/ 下只有一个需求的文件。

## 文档模板

```
docs/plan/
├── README.md           ← 概览
├── xxx-功能描述.md      ← 任务文件（语义化命名）
└── ...
```

**README.md**：

```markdown
---
title: 需求标题
tags:
  - tag1
  - tag2
keywords:
  - 关键词1
  - 关键词2
---

# [需求标识] 需求标题

## 需求描述

简要描述

## 核心功能

- [ ] 功能点 1
- [ ] 功能点 2

## 任务列表

- [ ] [用户登录](用户登录.md)
- [ ] [表单校验](表单校验.md)

## 关联规格

- [相关规格文档](../spec/xxx.md) — 将新增/更新（如有）

## 当前状态

- 阶段：开发
- 进度：2/5 任务完成
- 当前任务：用户登录.md
- 上次会话：2026-06-19
```

**任务文件**（需求理解有标题和待解决，任务规划细化其余部分）：

```markdown
# 任务标题

## 待解决

- 需要确认的问题（优先处理）
- 有多个技术方案时，提供方案对比

## 技术方案

- 功能归属：放在哪个包/模块
- 依赖关系：依赖哪些模块
- 接口设计：API 接口、数据结构
- 技术选型：使用哪些技术/库

## TODO

- [ ] 执行步骤 1
- [ ] 执行步骤 2

## 验收清单

- [ ] 功能点 1
- [ ] 功能点 2
```

## 流程

### 启动

1. 检查 `docs/plan/` 是否已有进行中的需求（README.md 存在）
   - **有** → 进入「进度恢复」
   - **无** → 检查 `docs/issue/` 是否有待办 issue
     - **有待办** → 列出待办 issue（标题 + priority + 简要描述），让用户选取或输入新需求
     - **无待办** → 提示用户输入需求描述（或先 `/issue` 捕获）
2. 如果从 issues/ 选取：将 issue 文件移入 `docs/plan/` 作为 README.md 的初始内容，更新 issues/README.md 索引为「进行中」
3. **等待用户明确指令**

### 进度恢复（启动时）

1. 读取 README.md 和任务文件
2. 总结当前进度（已完成/进行中/待开始的任务）
3. 向用户汇报，给出下一步建议
4. **等待用户明确指令**

### 需求理解

**信息收集**：
- 扫描项目结构（优先使用 codegraph，未安装时提示用户可选安装，回退到 Grep/Read）
  - 识别包/模块入口，获取导出列表
  - 识别页面目录、状态管理等关键结构
- 需求模糊时，逐项确认深入提问

**假设质疑**（信息收集完成后）：
- 对需求的每个方面持续追问，直到与用户达成共识
- 沿着决策树的每个分支深入，逐个解决依赖关系
- 每个问题给出推荐答案，让用户做选择题而非填空题
- 一次只问一个问题，避免信息过载
- 能从代码库找到答案的，自己探索后向用户确认

**产出**：docs/plan/README.md + 任务文件（标题 + 待解决）
**⏸ 等待用户确认后再进入任务规划**

### 任务规划

- **细化任务文件**：填充技术方案、TODO、验收清单
- 文件存在则更新，不存在则创建
- 如需拆分任务，先与用户确认
- **快速验证建议**：技术方案涉及以下情况时，主动建议在任务列表最前面插入一个 demo/POC 验证任务：
  - 引入新的第三方库/工具
  - 使用项目中没有先例的模式
  - 涉及跨包协作的新路径
  - 技术方案有多个候选需要验证
  - 用户也可以随时要求加 demo 任务
- **⏸ 等待用户确认后再进入开发**

### 开发执行

按 TODO 列表逐项执行。**默认采用 TDD 流程**：

#### TDD 开发（红-绿-重构）

对第一个未完成的 `- [ ]` 项，执行红-绿-重构循环：

1. 🔴 **Red**：先写一个描述预期行为的测试，运行确认它失败
2. 🟢 **Green**：写最少的代码让测试通过
3. 🔵 **Refactor**：优化代码结构，保持测试通过
4. 标记为 `[x]`，继续下一项

**TDD 豁免**：TODO 项可标记 `[no-tdd]` 跳过测试（如纯 UI 样式调整、配置变更、文档更新）。未标记的默认走 TDD。

#### 开发纪律

- 全部 TODO 完成后，执行 项目配置的 lint 和类型检查命令，修复问题直到通过
- **禁止自动 commit**，所有提交由用户手动控制
- **范围控制**：开发过程中发现的新任务或新需求，提醒用户 `/issue` 记录，不加入当前任务列表
- **动态拆分**：开发中发现需要拆分子任务时，新建 `<父slug>-<子slug>.md`，按需声明依赖

### 代码审查（每个任务完成后，可选）

如果项目配置了 code-reviewer agent（`.claude/agents/code-reviewer.md`），自动触发审查：

1. 调用 code-reviewer agent，传入当前任务变更的文件
2. 审查结果处理：
   - blocker → 必须修复后才能继续
   - risk → 评估后决定是否修复
   - improvement → 记录，可后续处理
   - uncertain → 提交用户确认
3. 修复后重新执行项目配置的 lint 和类型检查命令

如果未配置 code-reviewer，跳过自动审查，直接进入验收。

审查通过后，向用户汇报当前任务完成情况，列出验收清单内容供用户逐项确认。
**⏸ 等待用户验证功能实现** — 用户确认后标记验收清单，进入下一个任务或需求归档

### 需求归档（所有任务完成 + 用户确认后）

1. **写总结**：通过 git 记录提取完整 commit 信息，在 README 中增加「开发总结」章节（没有的内容不要编造）：
   - 功能增量：新增/修改了哪些功能
   - 规则增量：新增/修改了哪些业务规则
   - 影响范围：影响了哪些模块/功能
   - 风险记录：潜在风险点（如有）
   - 决策记录：技术决策及原因（如有）
2. **提取行为规格**到 `docs/spec/`（如项目有此目录）：
   - 从验收清单、技术方案、功能增量中识别涉及的业务模块
   - 对每个模块，检查 `docs/spec/{module}.md` 是否存在
     - 不存在：创建新 spec
     - 已存在：追加或更新相关内容
   - 未涉及业务行为变更时跳过此步
3. **归档**（目标：`docs/archive/{year}/`）：
   - 有对应 issue：将总结写入 issue 文件，移入归档目录（保留原文件名，如 `issue-001-slug.md`），更新 `docs/issue/README.md` 索引
   - 无对应 issue：将 README.md 重命名为 `{kebab-case-slug}.md` 后移入归档目录
   - 删除任务文件
